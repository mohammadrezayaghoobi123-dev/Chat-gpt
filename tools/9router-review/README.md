# Independent 9Router PR Review

This integration sends a pull-request diff to a configured 9Router OpenAI-compatible endpoint and posts a model-assisted report as an issue comment. It does not submit GitHub review approvals, merge, modify source files, deploy, or change repository settings.

## Required GitHub configuration

Add these repository Actions secrets only after a trusted 9Router instance and API key are available:

- `NINE_ROUTER_API_URL`: HTTPS API base URL, for example `https://9router.example/v1`.
- `NINE_ROUTER_API_KEY`: dedicated 9Router API key with the minimum required access.

Add this repository Actions variable:

- `NINE_ROUTER_MODEL`: exact model identifier configured in 9Router.

Never commit these values or paste the API key into issues, pull requests, or chat. The configured 9Router provider receives the pull-request patch; configure only an endpoint approved to receive this repository's source.

## Workflow trust boundaries

- `9router-pr-review-signal.yml` runs on `pull_request_target`, whose workflow definition is taken from the base repository's default branch rather than the PR merge commit. Its workflow and job permissions are empty; it creates a strict event-bound `signal.json` receipt from trusted GitHub event context and uploads that single file as a run/attempt-specific, one-day artifact. It does not check out pull-request code, execute PR code, or reference secrets. A PR cannot replace this signal workflow definition through its own diff.
- `9router-pr-review.yml` runs later on `workflow_run`, using its copy from the trusted default branch. It accepts only successful `pull_request_target` runs from the exact signal workflow path and verifies that both the PR head and base repositories are this repository.
- The privileged workflow downloads only the artifact matching the triggering run ID and API-verified run attempt. It validates the receipt, then independently reconciles workflow-run metadata and live PR state through read-only GitHub API calls. It does not execute or check out artifact contents.
- Fork-originated PRs are intentionally skipped by checking the associated PR's `head.repo.full_name`, not merely the workflow-run repository metadata. This first version reviews same-repository branches only.
- The privileged job checks out only the trusted default branch; it never checks out or executes pull-request code.
- The reviewer does not use `workflow_run.pull_requests` to select the causal PR. The receipt captures `github.sha` separately as `workflowSha`; the resolver binds `workflow_run.head_sha` to that trusted workflow revision, while independently checking the receipt's PR head/base snapshots against the live PR API. The reviewer rechecks both live PR SHAs before sending the patch to 9Router, after model generation, and immediately before append-only comment publication. If either side changes during those stages, the stale review is rejected. A residual race remains between the final metadata read and comment creation because GitHub does not provide a transaction spanning PR metadata and issue-comment creation.
- Missing file patches, empty diffs, oversized patches, invalid event provenance, and stale head SHAs stop the review instead of producing a partial or stale report. The cumulative formatted patch budget is enforced as each file is received, so pagination stops immediately when the 45,000-character ceiling is crossed rather than fetching later pages.
- Patch content and filenames are untrusted prompt data. The complete patch is passed as a JSON-encoded string rather than sentinel-delimited raw text, preventing patch contents from forging the prompt's closing delimiter. This framing does not eliminate semantic prompt injection; the model must still treat the decoded patch as data only.
- Model-generated reports are parsed with the pinned `marked@17.0.1` GitHub-flavored Markdown lexer and rebuilt from an explicit AST allowlist. Headings, paragraphs, emphasis, strikethrough, inline/fenced code, blockquotes, lists, tables, and horizontal rules are preserved. Link and image nodes are converted to inert text placeholders; raw HTML and reference definitions are discarded; bare URL/autolink nodes are replaced; unknown AST node types fail closed. Rebuilt text is escaped before Markdown serialization and GitHub mentions are neutralized. This is an AST-based structural sanitizer; GitHub's hosted renderer remains a separate rendering boundary and requires continued hostile regression coverage.
- The parser dependency is pinned to `marked@17.0.1` in `package.json` and `package-lock.json`; CI installs only the lockfile-resolved package with `npm ci --ignore-scripts` and verifies its registry signature and provenance using `npm audit signatures`. The locked package has no runtime dependencies; the latest verified run reported zero package vulnerabilities.
- Every GitHub API JSON response body is streamed with a 1 MiB hard byte ceiling before parsing; oversized bodies are canceled and rejected before subsequent review stages. The 9Router HTTP response body is separately streamed with a 512 KiB hard byte ceiling before JSON parsing; oversized bodies are canceled and rejected before comment lookup or publication. The sanitized model report is separately capped at 30,000 UTF-16 code units. Oversized output is rejected rather than truncated, preserving report integrity and leaving a conservative margin below GitHub's 65,536-character issue-comment limit.
- **Read-only publication reconciliation (Finding 26):** After model generation, the reviewer reads issue comments sequentially with `per_page=100` and scans at most 10 pages (1,000 comments) and 4 MiB of cumulative serialized comment data. Each individual GitHub response remains subject to the existing 1 MiB streaming cap. A page must be a valid array of records with string bodies and author logins; malformed records, API errors, rate limits, byte-budget exhaustion, or a full tenth page fail closed and prevent publication. A report matches only when its first body line is the exact deterministic head/base marker and its author login is `github-actions[bot]`. One match suppresses a duplicate POST; more than one match is an ambiguity and stops publication. User-authored lookalike markers do not suppress publication. The reconciliation path is GET-only: no prior comment is PATCHed or deleted. See [List issue comments](https://docs.github.com/en/rest/issues/comments#list-issue-comments-for-an-issue) and [REST API pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api).
- **Concurrency and recovery:** Review jobs are serialized per PR using a concurrency group keyed by PR number, with `queue: max`. GitHub permits at most 100 pending jobs in that group; additional jobs are canceled when the queue is full. GitHub processes queued jobs FIFO by the time they begin waiting, but does not guarantee ordering by workflow-dispatch time. Immutable head/base checks prevent stale jobs from publishing after the PR diff changes; they do not guarantee that every intermediate event is reviewed. If a comment POST succeeds remotely but its response is lost, a later rerun scans the bounded comment history and suppresses a duplicate when the exact bot-authored head/base marker is visible. If history cannot be scanned completely within the page/byte/deadline limits, the run fails closed. This reduces observable duplicates but does not provide exactly-once delivery or durable retry. This is best-effort delivery with bounded duplicate suppression, not exactly-once or guaranteed at-least-once delivery.
- **Comment provenance limitation:** A comment authored by `github-actions[bot]` is not cryptographic proof that this reviewer workflow created it. Another privileged workflow with comment-write permission could post a lookalike marker and cause this reviewer to suppress publication. This is a bounded denial-of-service / false-suppression risk, not a path to overwrite or mutate comments. Human readers must still treat comment authorship and report content as untrusted unless separately verified. A dedicated GitHub App identity or signed provenance would be needed for stronger attribution.
- Uses `GITHUB_TOKEN` only for reading repository contents and PR metadata/files and writing PR comments. No contents write, review approval, merge, or deployment permission is requested.
- Requires HTTPS for the 9Router endpoint and rejects embedded credentials, query parameters, and URL fragments.
- Suppresses API response bodies on errors to avoid leaking provider diagnostics or credentials into logs, and explicitly cancels unread non-success response streams to release transport resources.

## Review interpretation

Each finding must use one of `SUPPORTED`, `DISPUTED`, `REJECTED`, or `UNKNOWN`. `UNKNOWN` is not a pass or fail. The model is not a human reviewer and its report is not proof of correctness; findings require independent verification.


### Finding 21: Existing bot-comment identity was not a trustworthy update target — historical remediation superseded by Finding 26
- **Original finding:** Matching `github-actions[bot]` plus a predictable head/base marker did not prove that a comment was created by this exact reviewer workflow. Updating a matching comment could therefore mutate a forged or unrelated comment.
- **Historical TDD evidence:** run `45033942148`, 29 passed / 1 failed; run `45034129815`, 30/30 passed. At that stage, the selected mitigation was strict append-only publication with no history reads, PATCH, or deletion.
- **Superseding decision:** Finding 26 later approved bounded read-only reconciliation to suppress duplicates after ambiguous POST outcomes. The current implementation may GET comment history and use an exact bot-authored head/base marker only as a duplicate-suppression signal. It still never PATCHes or deletes existing comments.
- **Current residual risk:** `github-actions[bot]` is not cryptographic provenance. Another privileged workflow with comment-write permission could forge a matching marker and suppress publication. See Finding 26 for current limits and failure behavior.


### Finding 22: Per-PR concurrency is bounded serialization, not guaranteed delivery — residual operational risk
- **Classification:** **SUPPORTED** — GitHub documents that `queue: max` permits at most 100 pending jobs or workflow runs per concurrency group; further arrivals are canceled when the group is full. GitHub also documents that FIFO order is based on when a job begins waiting, not workflow dispatch time, so dispatch order is not guaranteed. References: [GitHub concurrency controls](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) and [Actions limits](https://docs.github.com/en/actions/reference/limits).
- **Existing safeguards:** The review job is serialized per PR. The resolver accepts exactly one same-repository PR and captures immutable head/base SHAs. The reviewer rechecks both SHAs after patch retrieval, after model generation, and immediately before comment publication. A stale queued run therefore fails closed rather than intentionally publishing a report for an obsolete diff.
- **Failure mode:** If more than 100 jobs are pending for the same PR, an additional signal's review job can be canceled. Earlier queued jobs may then reject themselves because their immutable SHA snapshots are stale. The system has no durable retry queue or automatic reconciliation pass, so a burst can leave the current PR head without a report until another qualifying event or a manual rerun occurs.
- **Ordering:** GitHub's queue order is not guaranteed to match event dispatch order. The immutable SHA checks protect report correctness for changed diffs, but they do not guarantee that every event is reviewed. Repeated events for the same head/base pair can still create duplicate append-only comments.
- **API recovery:** GitHub non-success responses are canceled and fail closed with a generic status error. The current client does not interpret `Retry-After` or rate-limit reset headers and does not retry 403/429/5xx responses. This avoids unsafe blind retries but means transient rate limiting or service errors stop that execution without a report. A later rerun is an operational recovery path, not an automatic guarantee.
- **Stale-work cost:** The 9Router request has a 120-second request timeout. If the PR changes after the pre-model SHA check, the in-flight model request is not actively canceled; the reviewer detects the changed SHA after the response and refuses publication. This preserves correctness but can spend up to the request timeout and delay the next serialized job.
- **UNKNOWN:** No real queue-saturation, out-of-order dispatch, GitHub rate-limit, or privileged workflow end-to-end test has been run. The workflow files are still absent from the default branch, and GitHub documents that `workflow_run`-triggered workflows run only when the workflow file exists on the default branch. The branch-only contract suite cannot prove hosted queue behavior.
- **Disposition:** No code change is made in this finding. Replacing immutable event snapshots with latest-state reconciliation, adding durable retries, or introducing idempotent report state changes the workflow's delivery semantics and needs a separate design decision. Current behavior is bounded and fail-closed, but it is not an at-least-once guarantee for every PR update.
### Finding 23: Independent request timeouts did not bound total review execution — remediated with an overall deadline
- **Classification:** **SUPPORTED** — the previous implementation applied a separate 120-second timeout to each GitHub request and the 9Router request, while the privileged Actions job had a 10-minute job timeout. Multiple sequential requests could therefore consume the entire job budget without an application-level execution deadline.
- **Worst-case request path:** one initial PR read, up to ten file-page reads, one pre-model SHA revalidation, one post-model SHA revalidation, one final pre-publication SHA revalidation, and one comment POST: up to 15 GitHub API requests, plus one 9Router completion request. The sum of independent 120-second ceilings was 32 minutes; this is a sum of per-request maxima, not a predicted normal runtime. The outer Actions job timeout remained the final hard stop.
- **Remediation:** runReview now starts one wall-clock deadline (8 minutes by default; accepted configuration is bounded to 1 ms–8 minutes). Every GitHub request and the 9Router request receives an abort signal capped by the lesser of the remaining overall budget and the existing 120-second per-request limit. The same signal remains attached while response bodies are consumed. When the deadline expires, the in-flight request is aborted; subsequent requests are rejected before network activity. The 10-minute Actions job timeout remains an outer safety boundary and includes checkout/dependency setup outside runReview.
- **TDD:** the new regression test simulates an in-flight GitHub request and verifies that the overall deadline aborts it. An initial hosted run exposed three compatibility/test-fixture failures: two existing tests lost their expected underlying error details, and the deadline fixture did not keep the event loop alive for Node's unreferenced timeout. The implementation now preserves original non-deadline errors, preserves response-size rejection details, and the fixture uses a bounded keep-alive timer. This failure evidence was used to refine the change rather than suppressing the tests.
- **GREEN evidence:** GitHub Actions run 45035554224, contract-tests job 137248396521: **31 passed, 0 failed, 0 cancelled**. Locked dependency installation and npm registry signature verification also completed successfully. Gitleaks PR-diff scans completed successfully on the resulting head.
- **Failure recovery policy:** GitHub non-success responses remain fail-closed; this change does not add automatic retries or interpret Retry-After/rate-limit reset headers. GET retries may be considered separately with bounded backoff and remaining-deadline checks. The append-only comment POST is deliberately not retried after ambiguous transport failure because GitHub may already have created the comment; blind retry can duplicate it.
- **Residual stale-work cost:** a PR change during model generation is still detected by the post-model SHA revalidation, not by actively polling/canceling on PR changes. The 9Router request is now bounded by the lesser of 120 seconds and the remaining overall deadline, which bounds this exposure but does not eliminate wasted inference.
- **UNKNOWN:** no live 9Router integration, privileged workflow_run end-to-end execution, hosted API rate-limit exercise, or queue/load test has been performed. The branch contract tests prove deadline propagation and cancellation behavior with a controlled fetch implementation, not all hosted transport semantics.
- **Disposition:** application-level execution is now bounded and fail-closed. Automatic recovery from transient GitHub failures remains intentionally deferred; no claim of exactly-once publication or guaranteed review delivery is made.

### Finding 24: GitHub API rate limits and authorization failures were collapsed into generic HTTP errors — remediated
- **Finding:** The API client previously discarded response headers and reported only a generic HTTP status. Operators could not distinguish a primary rate limit, a secondary rate limit, an authentication failure, a permission/rate-limit ambiguity, or a provider-side 5xx failure. Rate-limit recovery metadata was unavailable.
- **TDD RED:** run `45038428798`, contract-tests job `137257259937`: **35 passed, 1 failed**. The malformed-header regression demonstrated that fractional `Retry-After` and scientific-notation reset values were incorrectly accepted by permissive numeric/date parsing.
- **Remediation:** The client now classifies primary rate limits when a 403/429 response reports `x-ratelimit-remaining: 0`; classifies secondary rate limits when a 403/429 includes a valid `Retry-After`; keeps a bare 403 explicitly ambiguous as `forbidden-or-secondary-rate-limit`; classifies bare 429, 401, 5xx, and other HTTP failures separately. `Retry-After` accepts integer delta-seconds or an IMF-fixdate HTTP date; reset metadata accepts only digit-only values that are safe integers. The error message exposes only the whitelisted status, classification, and parsed wait/reset metadata. Response bodies are canceled and never parsed or logged.
- **TDD GREEN:** run `45038487813`, contract-tests job `137257443186`: **36 passed, 0 failed, 0 cancelled, 0 skipped**. Added deterministic coverage for primary and secondary rate-limit headers, ambiguous 403 handling, malformed numeric header rejection, HTTP-date parsing, and the no-automatic-retry fail-closed path.
- **Recovery decision:** No automatic retry or sleep was added. A blind retry of the append-only comment POST after an ambiguous transport outcome can create duplicate reports. The current behavior stops the run and exposes safe retry/reset metadata for operator-directed recovery; it does not implement automated backoff, durable retry, or reconciliation.
- **Residual UNKNOWN:** No hosted GitHub rate-limit event or live 9Router/privileged workflow execution has been exercised. Contract tests use controlled synthetic responses and prove classifier behavior, not GitHub's live rate-limit policy or delivery guarantees.
- **Disposition:** The error taxonomy and safe diagnostic metadata are **SUPPORTED** by contract tests. Automated recovery and hosted rate-limit behavior remain **UNKNOWN**.

### Finding 25: Comment publication has ambiguous-commit and non-idempotent retry semantics — residual delivery risk
- **Evidence in production path:** `runReview` performs one append-only `POST /issues/{pull_request}/comments` and returns success only after `requestJson` has consumed and parsed the successful response. There is no idempotency key supported by this call path, no durable publication ledger, and no reconciliation after an ambiguous network outcome.
- **Hostile reproduction:** contract test `an ambiguous POST timeout may produce a duplicate on append-only rerun` simulates GitHub creating the remote comment before the connection resets. The first invocation rejects despite the remote side effect; a rerun posts again. Assertions prove two remote comments, zero history reads, and zero PATCH operations. This is a deterministic demonstration of duplicate publication, not a live GitHub incident.
- **Queue boundary:** the workflow serializes valid reviews by PR and uses `queue: max`, but GitHub documents a maximum of 100 pending jobs per concurrency group; additional jobs are canceled. Queue order is based on when jobs begin waiting, not event-dispatch time. The workflow has no durable retry/reconciliation mechanism for canceled or stale runs.
- **Corrected delivery terminology:** the system is **best-effort, non-idempotent append-only publication with ambiguous commit outcomes**. A retry can duplicate a comment, while a canceled, stale, rate-limited, or otherwise failed run may leave the latest PR head without a report. It is neither exactly-once nor a guaranteed at-least-once delivery system.
- **Disposition:** **SUPPORTED** as a current architectural limitation by source inspection, existing contract tests, and GitHub Actions documentation. No production behavior was changed in this finding.
- **Design decision required before remediation:** (A) retain strict append-only behavior and accept/document duplicates and missed delivery; (B) perform read-only reconciliation using the deterministic head/base marker before POST, accepting history pagination, rate-limit, and race considerations; or (C) add a durable idempotency ledger/outbox, which introduces a stateful external dependency and operational cost. No option is selected by this audit.
- **Verification boundary:** no live queue-saturation, ambiguous hosted POST, or recovery E2E was run. The contract test validates the modeled failure mode, not a guarantee about every GitHub transport failure.

### Finding 26: Ambiguous publication reruns could duplicate reports — bounded reconciliation with authenticated provenance
- **Finding:** A comment POST can succeed remotely while the client loses the response. A rerun must reconcile the exact report before posting again, but the shared `github-actions[bot]` login and a public head/base marker are forgeable by another privileged workflow.
- **TDD RED — duplicate delivery:** run `45039307101`, contract-tests job `137259950593`: **35 passed, 1 failed** because the rerun made zero comment-history reads.
- **TDD RED — forged provenance:** run `45040563024`, contract-tests job `137263834391`: **39 passed, 1 failed**. A synthetic comment authored as `github-actions[bot]` with the exact unsigned head/base marker suppressed the new POST (`0 !== 1`), reproducing the trust flaw.
- **Remediation:** Reconciliation now accepts only a version-2 HMAC-SHA-256 marker. The signature binds the repository, pull-request number, exact head SHA, and exact base SHA; comparison uses constant-time byte comparison. A matching bot login without a valid signature, including the legacy unsigned marker, is ignored and cannot suppress publication. Existing comments remain append-only and are never edited or deleted.
- **Secret requirement:** The privileged workflow requires the repository secret `NINE_ROUTER_REVIEW_MARKER_KEY` with at least 32 bytes of high-entropy key material. Generate it outside the repository (for example, `openssl rand -hex 32`) and add it as a GitHub Actions repository secret. The value must never be committed, placed in a variable, printed, or pasted into chat. If it is absent, every privileged reviewer step is skipped; the reviewer does not silently fall back to unsigned reconciliation.
- **Trust boundary:** The HMAC prevents a different workflow that lacks this dedicated secret from forging a suppressing marker. It does not protect against repository administrators or a compromised trusted workflow that can read the secret. Keep this secret referenced only by the trusted reviewer workflow and audit workflow changes.
- **Bounded scan:** Sequential GET-only scan of at most 10 pages × 100 comments and 4 MiB cumulative serialized data, with the existing 1 MiB per-response cap and 8-minute overall deadline. Incomplete history, malformed records, API errors, multiple valid matches, or exhausted limits fail closed.
- **Residual delivery risk:** A race remains between reconciliation and POST; a newly posted comment may not yet be visible after an ambiguous transport outcome. This is not exactly-once delivery, a durable outbox, or guaranteed delivery.
- **Disposition:** HMAC-authenticated bounded reconciliation is implemented in the feature branch. Hosted contract tests and secret scans must pass on the final documentation head. Live privileged workflow / 9Router E2E and a real ambiguous hosted POST remain `UNKNOWN`.



### Finding 27: Marker-signing secret was exposed to every job step — scoped to two steps
- **Finding:** The dedicated HMAC key was defined in the privileged job-level environment, making it available to setup and dependency-installation steps that do not need it. This unnecessarily expanded the secret exposure surface.
- **TDD RED:** run `45041484659`, contract-tests job `137266692745`: **40 passed, 1 failed**. The workflow contract expected two scoped declarations (configuration validation and final review) but found one job-level declaration.
- **Remediation:** Removed all credentials and router secrets from the job-level environment. The configuration-validation step receives only the values needed to check readiness and exports a boolean output. Checkout, Node setup, dependency installation, and signature verification receive no marker key or router credentials. Only the final report step receives `GITHUB_TOKEN`, router credentials, and `NINE_ROUTER_REVIEW_MARKER_KEY`. All five privileged steps after configuration validation are gated on the readiness output.
- **TDD GREEN:** run `45041593586`, contract-tests job `137267029196`: **41/41 PASS**, zero failures, cancellations, or skips.
- **Residual trust boundary:** The configuration-validation step must read the marker secret to establish readiness, but it does not print or persist the value. The final report step is the only step that needs the key to sign and verify report markers.

## Finding 30 — edited-event cost amplification

- **Finding:** Adding the broad `edited` activity alone would also enqueue reviews for title/body edits. The reviewer currently generates the model report before bounded duplicate reconciliation, so repeated metadata-only edits could incur repeated 9Router calls even when the head/base SHA pair is unchanged.
- **TDD RED:** Commit `179d304bd46ff2655412622ec7df4f05c9136681` added a contract assertion requiring the signal job to gate `edited` events on `github.event.changes.base`. ### A — Event-bound signal receipt

The trusted `pull_request_target` signal workflow writes a fixed-schema `signal.json` using only values from the trusted GitHub event context. The receipt binds:

- repository name and numeric repository ID;
- workflow run ID and run attempt;
- event name and action;
- exact PR number;
- PR head and base SHAs;
- head/base repository names and base ref.

The workflow uploads only this file as `9router-pr-signal-<run_id>-<run_attempt>`, with one-day retention. The signal workflow has no checkout, no PR-code execution, no secrets, no router access, and no external network calls other than the GitHub artifact upload.

### B — Independent GitHub API reconciliation

Before downloading the artifact, the privileged workflow reads the authoritative `run_attempt` from `GET /repos/{owner}/{repo}/actions/runs/{run_id}` and checks run identity, event, workflow path, conclusion, repository identity, workflow ID, and head SHA. It downloads only the artifact belonging to that exact run ID and API-verified attempt.

The resolver then parses the bounded receipt and independently re-fetches both the workflow run and the PR. It checks the receipt against run ID/attempt, repository identity, workflow metadata, run SHA, PR number, open/non-draft state, head/base SHAs, base ref, and repository identities. It never reads or selects from the API's `pull_requests` array. The verified PR number becomes the downstream job output and is the only source for per-PR concurrency.

The resolver job has read-only `actions`, `contents`, and `pull-requests` permissions. Router credentials and the review-marker key are not available to it.

### C — Fail-closed execution gate

The reviewer job depends on successful receipt verification. Missing or malformed receipts, wrong run/attempt, wrong workflow, repository mismatch, stale PR snapshots, closed/draft PRs, API errors, or any SHA mismatch stop the chain before model inference and comment publication. The downloaded artifact is parsed as data only; it is never executed or checked out.

### Finding 45 — publication is serialized, but not provably exactly-once (2026-11-22)

- **Question:** can duplicate `workflow_run` events or reruns publish multiple comments for the same PR head/base snapshot?
- **Controls verified in source:** the privileged `review` job uses one concurrency group per validated PR number, `queue: max`, and does not cancel an in-progress review. Therefore review jobs for the same PR are serialized by the workflow concurrency mechanism; duplicate resolver executions may occur, but their downstream review jobs enter the same PR-scoped queue. The reviewer performs a bounded read-only scan of up to 10 pages / 1,000 comments / 4 MiB, accepts only an exact HMAC marker from `github-actions[bot]`, rejects multiple matches, and skips model inference when one matching report is visible.
- **Existing tests:** `review.test.mjs` asserts the PR-scoped concurrency group, bounded queue, and no `cancel-in-progress`; it also tests duplicate suppression when a matching report is visible and tests an ambiguous POST whose created comment is immediately visible on the next run.
- **Hostile gap:** the ambiguous-POST test models immediate read-after-write visibility. It does not model a successful remote POST followed by a temporarily stale comment-list response. If GitHub accepts the POST but the client loses the response, and a subsequent serialized run cannot yet observe the created comment in the bounded history scan, the second run can infer and POST again. Per-PR serialization prevents overlapping reviewer jobs; it does not provide a server-side idempotency key or atomic compare-and-create operation for issue comments.
- **Why no speculative patch:** adding a finite number of immediate re-reads or sleeps cannot establish exactly-once publication without a documented read-after-write consistency guarantee. A durable external idempotency ledger or a GitHub publication primitive with a uniqueness/CAS contract would be needed for a stronger guarantee; neither is currently part of the approved architecture. Do not claim exactly-once or at-most-once delivery.
- **Disposition:** **SUPPORTED** — serialization and visible-marker duplicate suppression are implemented and contract-tested. **UNKNOWN** — behavior under delayed comment visibility after an ambiguous successful POST. This is a residual distributed-systems limitation, not a demonstrated exploit against GitHub's current consistency behavior.

### Finding 46 — comment identity and offset-pagination limits (2026-11-22)

- **Identity gate verified:** reconciliation requires the exact GitHub API login `github-actions[bot]` before considering a comment, then independently verifies the complete v2 HMAC marker. A copied marker from another PR, an unsigned legacy marker, a modified signature, or a valid marker attached to a non-bot author cannot suppress publication. The HMAC binds repository, PR number, head SHA, and base SHA. The API comment object also exposes a numeric user ID, but the current implementation does not pin that ID; this is recorded as a hardening opportunity, not a demonstrated bypass.
- **Pagination grounding:** the GitHub REST issue-comments endpoint documents ascending-ID ordering by default. The reviewer requests 100 records per page, scans at most 10 pages, and fails closed when the page ceiling is reached. New comments normally append after earlier IDs, so ordinary concurrent comment creation does not shift already-read earlier pages.
- **Residual mutation race:** REST pagination uses page-number offsets, not a snapshot cursor. If comments are deleted from an earlier page while a multi-page scan is in progress, later records can shift across page boundaries. In a constructed boundary case, deletion of an item from page 1 after page 1 was read can move the original first item of page 2 to the end of page 1; page 2 then starts one item later and can miss that report. If the missed record was a matching signed bot report, reconciliation could incorrectly proceed to another POST. This requires concurrent deletion during the scan and is not shown to have occurred in the hosted workflow.
- **No unsupported repair:** adding a fixed overlap or retry count cannot guarantee a stable snapshot under arbitrary concurrent deletions. A cursor-based source or durable idempotency mechanism would be needed to make a stronger claim. The current REST scan remains bounded and fail-closed for incomplete page-limit cases, but it is not snapshot-isolated.
- **Disposition:** **SUPPORTED** — author-login plus HMAC validation is present in code. **SUPPORTED** — the API documents ascending-ID order and the implementation uses bounded page offsets. **UNKNOWN** — whether concurrent deletion can occur during the real hosted reconciliation window and whether it has ever caused a skipped matching report. No bypass or duplicate publication was observed.
- **Scope:** documentation-only commit on `feature/9router-abc-provenance`; no code, workflow, secrets, repository settings, rulesets, Actions policy, `main`, merge, deployment, or Production change.


### Finding 47 — bot principal pinning and HMAC key rotation (2026-11-22)

- **Bot principal validation:** reconciliation currently checks `comment.user.login === "github-actions[bot]"` and then validates the HMAC. It does not check `comment.user.id` or `comment.user.type`. The login check is a useful identity gate, but the implementation does not bind the expected principal to a stable numeric account identifier. Public GitHub ecosystem references consistently associate the built-in `github-actions[bot]` account with numeric ID `41898282`; the GitHub `actions/create-github-app-token` documentation also demonstrates resolving a bot's ID from its `[bot]` slug rather than assuming all bots share one ID. This is supporting ecosystem evidence, not a live API identity verification for this repository's comment author.
- **Threat boundary:** a forged comment by an ordinary user remains rejected because the login must match and the HMAC must be valid. Pinning the expected numeric ID would further reduce dependence on login-only matching, but the implementation currently uses the repository's built-in `GITHUB_TOKEN` identity; do not generalize the constant to a future GitHub App bot without verifying that app's distinct ID.
- **Key-rotation behavior:** the marker format is v2 and carries head SHA, base SHA, and HMAC, but no key identifier. The reviewer receives one `NINE_ROUTER_REVIEW_MARKER_KEY` value and verifies existing comments only against that active key. After replacing the secret with a new key, previously valid comments signed by the retired key no longer match; a rerun for the same PR/head/base can therefore fail to recognize the old report and publish a duplicate. This is a deterministic consequence of the current single-key verification path, not a hypothetical cryptographic break.
- **No silent workaround:** retaining the old key forever is not an acceptable default rotation policy. A safer future design is a bounded verification key ring (current signing key plus explicitly time-bounded previous verification key(s)), with one current key used for new signatures, constant-time comparison for every candidate, a documented overlap/retirement window, and tests for current-key acceptance, previous-key suppression, expired-key rejection, and unknown key versions. If a key identifier is added to the marker format, it must be authenticated as part of the signed payload and versioned compatibly.
- **Disposition:** **SUPPORTED** — current source checks the bot login but not numeric ID/type. **SUPPORTED** — current marker verification uses one configured key and the marker contains no key ID. **SUPPORTED** — replacing that key makes old signatures unverifiable and can cause duplicate publication for the same snapshot. **UNKNOWN** — whether key rotation has ever occurred in this repository or produced a duplicate.
- **Required future TDD:** before implementing either principal pinning or a key ring, add regression tests first and observe the expected RED result. Do not change the workflow or secret configuration as part of this finding.
- **Scope:** documentation-only commit on `feature/9router-abc-provenance`. No secret values read or changed; no code, workflow, repository setting, ruleset, Actions policy, `main`, merge, deployment, or Production change.

### Finding 56 — per-PR concurrency queue ordering and saturation (2026-11-23)

- **Question tested:** does the current per-PR Actions concurrency group guarantee that every validated PR snapshot will eventually be reviewed, in event-dispatch order, under bursts or a saturated queue?
- **Configured behavior:** the privileged `review` job uses `group: 9router-pr-review-${{ needs.resolve-signal.outputs.pull_request }}` and `queue: max`, with no `cancel-in-progress: true`. The key is the validated PR number, so review jobs for the same PR in this repository share one concurrency group. The `resolve-signal` job runs before this group is entered and is not serialized by it.
- **Platform contract:** current GitHub Actions documentation states that a concurrency group permits at most one running job and, with `queue: max`, up to 100 pending jobs. When the queue is full, additional jobs are canceled. GitHub also documents that queue processing order is based on when jobs start waiting on the group, not workflow dispatch time; ordering is therefore not guaranteed to match webhook/event order. `queue: max` cannot be combined with `cancel-in-progress: true`.
- **Stale-snapshot protection:** the reviewer does not trust queue position as evidence of freshness. It compares the live PR's head and base SHAs against the receipt-derived expected snapshot before work, after patch retrieval, before model inference, after model generation, and at the final publication gate. A queued job for an obsolete snapshot therefore aborts at a live-state gate instead of intentionally publishing a stale report. This is consistent with the earlier Finding 38 contract.
- **Hostile saturation case:** if one PR accumulates more than 100 pending review jobs while one job is running, GitHub cancels additional jobs entering the full queue. The canceled job can be the newest event/snapshot. The existing workflow has no durable coalescing/re-enqueue mechanism that guarantees the latest snapshot will be reviewed after saturation. A later PR event may create another run, but that is not an eventual-delivery guarantee. The Actions run history exposes cancellation; the current reviewer workflow does not automatically recover from queue saturation.
- **Ordering case:** because queue order is based on the time each job begins waiting, two signal runs dispatched in one order can reach the review queue in another order after independent resolver execution. The snapshot gates make older work fail closed; they do not guarantee FIFO by event dispatch or that the latest event is the last queued job.
- **Test coverage:** the existing contract test asserts the PR-number concurrency key, `queue: max`, and absence of `cancel-in-progress: true`. Existing runtime tests cover stale head/base snapshot rejection. These are source/contract guarantees; they do not simulate GitHub's hosted scheduler or its 100-pending-job saturation behavior.
- **Hosted execution boundary:** the current Actions history contains no `workflow_run` event runs. The default branch `main` still contains neither `.github/workflows/9router-pr-review.yml` nor `.github/workflows/9router-pr-review-signal.yml`; the files exist on this feature branch only. Therefore no live signal → resolver → queued reviewer execution, queue ordering, or saturation behavior has been observed in this repository.
- **Disposition:** **SUPPORTED** — the configured per-PR serialization and stale-snapshot checks are present; the documented queue cap and non-dispatch-ordering behavior create a bounded-delivery limitation. **UNKNOWN** — whether this repository has ever reached queue saturation, how real hosted events will interleave after default-branch activation, and whether a later independent event will recover a canceled latest-snapshot job. No claim of eventual delivery is made.
- **Decision:** no workflow code change is justified by the evidence. Replacing `queue: max` with the default single-pending behavior would make pending-run replacement more aggressive; enabling cancellation could terminate an in-flight publication path. Both would weaken the current non-canceling intent. A future reliability improvement should be a separately designed, least-privilege reconciliation mechanism that detects canceled/missing latest-snapshot work and safely re-enqueues only after independently checking the live PR. It must be threat-modeled and tested before implementation.

It does not explicitly establish that a reviewer workflow run always emits the required completion event when its only job is canceled while waiting in a concurrency queue, nor that the canceled job is always present with a stable ID/name. These scheduler behaviors remain **UNKNOWN** until isolated hosted evidence exists.
- **Read-only observer contract:** a future observer may only classify, never re-run, in this phase. It must (1) validate the triggering reviewer workflow identity/path/repository and authoritative run metadata; (2) list all job pages and attempts and require exactly one unambiguous reviewer job record; (3) parse a strict job-name grammar and compare PR/head/base/signal run/attempt; (4) retrieve the original signal run and exact attempt receipt and verify its artifact digest/schema while still retained; (5) read the live PR and classify snapshot equality/open/non-Draft state; and (6) record `SUPPORTED`, `DISPUTED`, or `UNKNOWN` with reason. Missing job record, expired receipt, multiple matches, incomplete pagination, rate limit, or API ambiguity must fail closed. No Actions write permission is needed for this read-only observer.
- **Decision:** the read-only observer is architecturally feasible as a future third-level workflow, but it is not implementable or testable in this repository's current default-branch state. A dynamic job name plus read-only job listing is necessary but insufficient: durable receipt availability and actual queued-cancellation event/job persistence are still unproven. Do not add observer workflow code, extend artifact retention, create external storage, grant permissions, or attempt re-runs in this finding.
- **Disposition:** **SUPPORTED** — `needs` is allowed in `jobs.<job_id>.name`; the Actions jobs API exposes named job records and supports read-only inspection; current contract tests and both secret scans passed; Signal receipt retention is one day; the required 9Router workflows are absent from default branch; and no `workflow_run` events are present in the queried run history. **UNKNOWN** — job record persistence for concurrency-canceled pending jobs, the exact workflow-run completion event sequence for that cancellation, and reconciliation after receipt expiration.
- **Scope:** documentation-only addition on `feature/9router-abc-provenance`; no source/workflow code, permission, secret, repository setting, default branch, merge, deployment, or Production change.


### Finding 61 — receipt expiry, metadata-only evidence, and bounded recovery horizon (2026-11-23)

- **Question tested:** can the system make an authenticated snapshot decision after the one-day Signal receipt artifact expires, using only workflow-run and artifact metadata?
- **Current configuration:** `9router-pr-review-signal.yml` uploads the event-bound receipt as `9router-pr-signal-{run_id}-{run_attempt}` with `retention-days: 1`. The repository is public and its default branch is `main`. GitHub's current documentation permits public-repository artifact retention from 1 through 90 days; a per-artifact retention value can be customized, subject to repository/organization limits. A retention change applies only to newly created artifacts, not existing ones.
- **Artifact API evidence:** GitHub's artifact REST API exposes metadata including artifact ID, name, size, `expired`, `created_at`, `expires_at`, digest, and associated workflow-run identity. The download endpoint returns `410 Gone` for an expired artifact. Therefore an expired artifact may remain discoverable as metadata for some time, but its receipt bytes are not recoverable through the artifact download endpoint. Do not treat the metadata digest as a substitute for receipt bytes or as proof that the receipt's schema and contents were validated by the observer.
- **Deletion boundary:** GitHub documents that deleting a workflow run also deletes all associated artifacts. Artifact metadata visibility is therefore not a durable archive guarantee. A controller must not assume an artifact record will remain available indefinitely after expiry or run deletion.
- **Current repository evidence:** the repository is public with default branch `main`. The Signal and Reviewer workflows are still absent from `main`; the latest branch push test run `45073060655` and secret scan runs are not Signal event runs and produced no artifacts. The queried history contains no actual hosted Signal → Reviewer → Observer execution from which to infer post-expiry behavior. No real expired receipt was available for a controlled API test.
- **Evidence classification after expiry:** if the original receipt bytes cannot be downloaded and independently digest/schema-validated, the observer may report only that a matching artifact metadata record was or was not found. It cannot assert the exact PR/head/base tuple from that artifact. The run metadata and artifact metadata may help locate the event, but they do not reconstruct the original receipt. Snapshot identity must be classified **UNKNOWN** unless another independently trusted source contains the full event-bound tuple and its integrity proof.
- **Bounded-horizon option:** increasing the Signal artifact's retention to 90 days would provide a longer bounded recovery window for a public repository, subject to repository/organization limits. It would not provide durable retention, and it increases the period during which PR metadata remains stored. Because this is a security/privacy and storage tradeoff, do not change the current one-day setting in this finding. If later approved, the change must be made only on the isolated feature branch, applies only to future receipts, and must be documented as a 90-day maximum recovery horizon—not permanent evidence retention.
- **Long-term evidence option:** if recovery beyond the artifact retention horizon is a hard requirement, the design needs a separately governed durable evidence store or a cryptographically verifiable append-only record with explicit writer identity, retention, deletion, access, and key-rotation controls. A GitHub artifact, mutable PR comment, branch name, workflow-run timestamp, or artifact digest without the original bytes is not by itself a durable immutable ledger. No external store, new permission, OIDC grant, attestation workflow, or repository policy is introduced here.
- **Observer fail-closed contract:** (1) query the exact workflow run and paginate artifact records; (2) match exactly one artifact by run ID, attempt-bound name, repository, and expected workflow; (3) check `expired`, `expires_at`, artifact ID, and digest; (4) download the artifact and verify the archive digest and receipt schema before the expiry boundary; (5) reconcile the receipt with authoritative run metadata and the live PR; (6) if the artifact is expired, deleted, unavailable, ambiguous, or its bytes fail validation, return `UNKNOWN` and stop. Do not fall back to timestamps, job names, PR current state, or a digest string to reconstruct the missing receipt.
- **Tooling caveat:** the connected GitHub artifact-list wrapper currently returns only the first page. A production observer must use the REST API with pagination and explicit run/attempt correlation; first-page results cannot support a completeness claim when pagination is present.
- **Decision:** the current one-day retention makes recovery intentionally short-lived. The correct response to expiry is loss of recoverable snapshot proof, not inference. A 90-day setting is a possible bounded operational improvement but is deferred pending an explicit retention/privacy decision. Long-term recovery requires a separately reviewed durable-evidence design.
- **Disposition:** **SUPPORTED** — current receipt retention is one day; the repository is public; public artifact retention is configurable from 1 to 90 days subject to policy; artifact metadata includes expiry and digest fields; expired downloads return 410; deleting a workflow run deletes its artifacts; and no relevant Signal artifact exists in the inspected branch test runs. **UNKNOWN** — actual post-expiry metadata availability duration for this repository, any hosted Signal receipt lifecycle, and any durable evidence source outside Actions artifacts.
- **Scope:** documentation-only addition on `feature/9router-abc-provenance`; no workflow/source changes, retention changes, permissions, secrets, repository settings, external storage, default branch, merge, deployment, or Production changes.


### Finding 62 — durable evidence architecture comparison (2026-11-23)

- **Question tested:** which evidence architecture can preserve and later verify the exact Signal event snapshot after the one-day Actions artifact expires or its workflow run is deleted?
- **Property separation:** integrity means bytes have not changed relative to a known digest; authenticity means a trusted identity is bound to the bytes or claim; availability means the bytes can still be retrieved; immutability means the relevant actor cannot silently rewrite or remove the record; timestamping means there is independently verifiable evidence that a claim existed by a particular time; retention defines how long the storage system promises to keep it. These properties are independent. A digest alone does not establish authorship or time. A signature alone does not guarantee availability or protect a signing key from compromise.
- **Option A — GitHub Actions artifact retention:** lowest implementation complexity and already integrated with the Signal/Resolver design. It preserves the original receipt bytes only during its configured retention horizon; digest checking protects transfer integrity while bytes remain available. It does not provide independent long-term availability, an external timestamp, or protection against deletion of the workflow run and its artifacts. Extending retention to 90 days is a bounded operational window, not a durable ledger. **Disposition: SUPPORTED for short-term recovery; REJECTED as the sole long-term archive.**
- **Option B — signed Git commit on a dedicated evidence branch:** a verified commit signature can bind the commit contents and parent history to a signing identity, subject to key custody and verification policy. Git commit author/committer dates are not a trusted timestamp authority. A branch is a movable reference; an append-only convention is not immutability. Rulesets can block force pushes/deletions and require signed commits, but privileged bypass identities and repository administration remain trust boundaries. The current evidence branch is reported unprotected and the current Finding 61 commit is unsigned, so those protections are not present in the inspected state. An independently published checkpoint is still needed to detect history rewrite. **Disposition: CONDITIONALLY SUPPORTED as a tamper-evident working ledger only after governance and external anchoring; not independently immutable.**
- **Option C — GitHub Artifact Attestations:** the documented model signs provenance claims using Sigstore and OIDC and binds them to a subject digest, repository, workflow, commit, and triggering event. For public repositories, GitHub documents a copy in its immutable public transparency log; Free-plan public repositories are eligible. GitHub recommends attestations for release software, binaries, packages, and manifests containing hashes, and explicitly advises against signing individual files such as source or documentation files. Therefore, do not attest each raw Signal JSON receipt as an isolated file. A possible future fit is a canonical, schema-versioned evidence manifest that contains the complete event-bound tuple plus the receipt digest, generated only after strict validation, then attested as a manifest. The attestation would prove the workflow provenance of that manifest; it would not independently prove that every field is semantically true unless the manifest-generation workflow validates those fields against authoritative GitHub event/API data. The manifest bytes still need durable storage. Generation requires additional workflow permissions including `id-token: write` and `attestations: write`; those permissions are not currently authorized or added. Attestations can also be deleted from the GitHub repository interface/API, so preserve and verify the bundle/transparency proof independently rather than treating the repository listing as the only copy. **Disposition: PROMISING for provenance and timestamp transparency of a canonical manifest; insufficient alone for payload availability.**
- **Option D — immutable GitHub Release assets:** a release can bundle a periodic evidence checkpoint. When release immutability is enabled, published assets cannot be added, replaced, or deleted and the associated tag cannot be moved or deleted while the release exists; release attestations can support integrity and origin verification. This is better suited to periodic batch checkpoints than one release per PR event. It remains in the same repository/account administrative trust domain, can expose PR metadata publicly, and requires repository-level enablement for future releases. It does not by itself establish independent availability if the repository/account is lost or the release lifecycle is otherwise disrupted. **Disposition: CONDITIONALLY SUPPORTED as a low-frequency public checkpoint, not an independent archive.**
- **Option E — independently governed append-only evidence store:** strongest separation if the store is in a different administrative/security domain and enforces object-lock/WORM retention, versioning, deletion controls, least-privilege writers, independent read credentials, retention/legal-hold policy, key rotation/revocation, and periodic externally verifiable timestamp or transparency-log anchoring. Store the exact canonical receipt/manifest bytes, not only a hash. A second region or separately controlled backup is needed for availability. This option has the highest operational, cost, and account-governance burden; no provider or service is selected in this finding. **Disposition: best fit for a hard long-term recovery requirement, but UNKNOWN until a provider, retention SLA, threat model, and recovery test are approved.**
- **Threat-model conclusions:** (1) workflow-run deletion defeats artifact-only recovery; (2) a digest without the original bytes cannot reconstruct a receipt; (3) a signed commit or attestation depends on identity and key/OIDC trust; (4) repository administrators or ruleset bypass actors remain a same-domain risk; (5) commit timestamps are not trusted timestamps; (6) an independent store can still fail through account loss, policy changes, compromised writers, or provider compromise; (7) public release assets, transparency logs, and manifests create data-minimization and privacy exposure; (8) no storage choice can prove the original event if the trusted signal workflow itself was compromised at capture time.
- **Recommended staged architecture:** keep the current one-day artifact as the immediate transport handoff; consider 90-day retention only after an explicit privacy/storage approval; if long-term proof is required, define a canonical evidence manifest containing the full event-bound tuple and receipt bytes or a durable reference, attest that manifest using a narrowly scoped trusted workflow, retain the manifest and attestation bundle in a separately governed WORM-capable store, and periodically anchor a digest/checkpoint in an independently controlled transparency mechanism. A protected evidence branch or immutable Release may be a convenience mirror, never the sole trust anchor. The observer must still verify the manifest schema, exact repo/workflow/run/attempt/PR/head/base tuple, attestation signer/workflow identity, transparency proof, and live PR state; absent or ambiguous evidence remains **UNKNOWN**.
- **Decision:** no single GitHub-native feature satisfies integrity, authenticity, availability, immutability, and trusted timestamping simultaneously. The lowest-complexity near-term choice remains the current artifact with its explicit short recovery horizon. The preferred long-term direction is an attested canonical manifest plus independent retention and external anchoring, subject to a separate design review and approval. A dedicated Git branch or Release alone is not an adequate immutable ledger.
- **Implementation boundary:** this finding is an architecture comparison only. No retention extension, source/workflow change, artifact attestation, OIDC permission, new secret, branch ruleset, release immutability setting, external account/store, Actions permission, repository setting, default-branch change, merge, deployment, or Production change is authorized or performed.
- **Disposition:** **SUPPORTED** — GitHub documents OIDC/Sigstore provenance attestations, subject digests, public transparency-log publication, the recommended artifact classes, attestation deletion controls, signed-commit/ruleset capabilities, and immutable release asset/tag behavior. **CONDITIONALLY SUPPORTED** — signed evidence branch and immutable Release as same-domain tamper-evident/checkpoint mechanisms under additional governance. **UNKNOWN** — actual account-specific availability of release immutability, applicable policy/bypass configuration, independent store suitability/cost, and whether a canonical event manifest can be generated and independently validated end-to-end.

### Finding 63 — canonical evidence manifest contract and independent recovery protocol (2026-11-23)

- **Objective:** specify a versioned, minimal, independently verifiable record that binds the exact Signal receipt bytes to the GitHub event, trusted workflow execution, repository identity, and PR snapshot. This is a design contract, not an implementation claim.
- **Trust-boundary rule:** fields inside a receipt or manifest are assertions until reconciled with an authoritative source. The verifier MUST NOT treat a self-reported run ID, repository name, workflow path, branch name, SHA, timestamp, artifact ID, or status as authoritative merely because it appears in signed or hashed JSON. A valid attestation proves the signer workflow made a statement about a subject; it does not prove every user-controlled predicate field is true. GitHub explicitly warns that statement predicate values may be controlled by the originating workflow, while certificate identity and verified transparency/timestamp values have distinct cryptographic status. The signer workflow therefore needs trusted-builder isolation and independent API reconciliation.
- **Canonical encoding:** use UTF-8 JSON constrained to I-JSON and RFC 8785 JSON Canonicalization Scheme (JCS) before hashing. Reject duplicate object property names, invalid Unicode, non-finite numbers, unknown schema versions, missing required fields, and out-of-range values. Do not normalize Unicode strings or reorder arrays. Encode large identifiers as decimal strings when cross-language numeric precision is not guaranteed. Define all digests as lowercase hexadecimal SHA-256 with an explicit `sha256:` prefix. The exact original receipt bytes MUST also be preserved; canonicalization is for deterministic manifest hashing, not permission to rewrite the source receipt.
- **Manifest schema v1 (normative field contract):**
  - `schemaVersion`: exact string `1.0`.
  - `subject`: `repositoryId` (immutable numeric GitHub repository ID represented as a decimal string), `repository` (canonical owner/name for display), and `pullRequestNumber` (positive integer).
  - `event`: `eventName`, `action`, `signalWorkflowId`, `signalWorkflowPath`, `signalWorkflowRef`, `signalWorkflowSha`, `signalRunId`, and `signalRunAttempt`. Workflow/run identifiers MUST be reconciled with GitHub's workflow-run API; the path, ref, and SHA are not trusted solely because the manifest says so.
  - `snapshot`: `headRepositoryId`, `headSha`, `baseRepositoryId`, and `baseSha`. Repository IDs and SHAs are authoritative only after comparison with the original event-bound receipt and the appropriate GitHub API response. Branch names, if later added for display, MUST NOT be used as identity keys.
  - `receipt`: `artifactId`, `artifactName`, `mediaType`, `byteLength`, and `sha256` of the exact downloaded receipt bytes. Artifact metadata is a locator and corroborating metadata, not a substitute for the receipt bytes.
  - `capture`: `recordedAt` as an informational producer timestamp only. It MUST NOT be treated as a trusted timestamp or used to resolve conflicting snapshots.
  - No secrets, tokens, router credentials, HMAC keys, prompt content, model inputs/outputs, or unnecessary personal data may be included.
- **Attestation envelope:** if adopted, the canonical manifest file is the in-toto Statement subject, with its SHA-256 digest, a dedicated versioned predicate type URI, and a narrowly scoped trusted workflow identity. Do not attest each raw Signal JSON file independently. The predicate carries the event/run/PR tuple for policy evaluation, but the verifier MUST independently validate it against authoritative GitHub API data because predicate fields can be workflow-controlled. Verify the repository ID, owner, exact signer workflow identity/path, expected predicate type, subject digest, and verified transparency timestamp. A repository name alone is insufficient because names can be reused after rename/deletion; bind the immutable repository ID as an additional policy check.
- **Authoritative verification order (all gates required):**
  1. Resolve the repository by expected immutable repository ID and reject a same-name/different-ID repository.
  2. Verify the attestation bundle cryptographically against an independently obtained trusted root; require the expected public-repository Sigstore trust domain, signer repository ID, exact signer workflow identity/path, and predicate type. Record the verified transparency timestamp separately from producer `recordedAt`.
  3. Verify the attestation subject digest against the exact canonical manifest bytes; reject missing, duplicate, extra, malformed, or ambiguous subjects.
  4. Validate manifest schema and strict field bounds; reject duplicate JSON keys before canonicalization.
  5. Query GitHub Actions for the exact repository/run/attempt and reconcile workflow ID, path, event, conclusion, head SHA, run attempt, and artifact identity. Do not rely on the first page of a connector wrapper; paginate the authoritative REST API and select the exact attempt.
  6. Retrieve the exact receipt bytes from the exact run/attempt artifact while available; verify byte length, SHA-256, artifact identity, and strict receipt schema. Compare every overlapping field to the manifest and authoritative run metadata.
  7. Query the live PR and classify snapshot validity independently: exact open/non-Draft head/base match is current; a changed head/base is SUPERSEDED; closed/Draft is not reviewable; unavailable or ambiguous API data is UNKNOWN. Historical evidence remains immutable even when the live PR changes.
  8. Emit a structured verification result with individual gate outcomes and source references. Never collapse a partial pass into overall success.
- **Outcome lattice:** `SUPPORTED` only when every required identity, signature, digest, schema, run/attempt, receipt, and snapshot gate passes. `DISPUTED` when two authoritative sources conflict. `REJECTED` for a demonstrably invalid signature, digest, schema, or identity mismatch. `UNKNOWN` for missing/expired/deleted bytes, unavailable API, incomplete pagination, unavailable trusted roots, ambiguous attempt, or any unverifiable required field. `SUPERSEDED` is a temporal validity label for a historically supported snapshot whose live PR head/base has changed; it is not evidence that the historical receipt was false.
- **Independent recovery package:** preserve together (a) exact original receipt bytes, (b) canonical manifest bytes, (c) attestation bundle, (d) trusted-root snapshot plus retrieval time and source, (e) repository-ID and signer-policy configuration version, and (f) a small verification report with tool/version and all gate results. A manifest hash without the manifest/receipt bytes is not recovery. A bundle without trusted roots or a pinned signer policy is not independently verifiable. Offline verification is possible only after the bundle and trusted roots have been exported; trusted roots must be refreshed as Sigstore keys rotate, while retaining the historical root material needed for past verification.
- **Recovery test matrix (must be run before any production adoption):**
  - Baseline: retrieve the complete package from a separately controlled recovery account/environment; verify exact bytes and all gates without access to the original workflow runner.
  - Mutation: flip one receipt byte, one manifest byte, subject digest, PR number, head SHA, base SHA, run attempt, workflow ID/path, and repository ID individually; each must fail at the corresponding gate.
  - Substitution: use a valid bundle from a different repository, different workflow, different predicate type, or same-name replacement repository; each must be rejected.
  - Replay: use a prior run attempt or older PR snapshot while the live PR has moved; historical evidence may verify, but must classify SUPERSEDED and must not authorize a new review/comment.
  - Missing evidence: remove receipt bytes, bundle, trusted roots, API pages, or exact run attempt; each must produce UNKNOWN, never a fallback to branch name, timestamp, artifact digest metadata, or current PR state.
  - Canonicalization: equivalent JSON objects with different key order/whitespace must produce the same JCS digest; duplicate keys, invalid Unicode, invalid numbers, and unsupported versions must fail.
  - Recovery independence: restore from a different account/security boundary and prove the verifier does not depend on the original GitHub account, runner filesystem, or the same storage credentials.
  - Destructive lifecycle tests (delete run/artifact, revoke credentials, rotate keys) MUST use a disposable test repository and separately approved test plan; do not run against this repository or existing PR evidence.
- **Residual risks:** a compromised trusted Signal workflow can emit a false but correctly attested manifest; a compromised signer workflow can make arbitrary predicate claims; repository admins can change workflows and trust policy unless independently anchored; API data can be unavailable; a transparency timestamp proves a signed statement existed by a time, not that its semantic contents were true; external storage can lose data or change policy; offline trusted roots can become stale. Mitigate with a protected reusable trusted-builder workflow, independent API reconciliation, repository-ID pinning, separately controlled storage credentials, key/root rotation procedures, and periodic recovery drills.
- **Decision:** accept this schema and verification sequence as the proposed v1 contract for further review. Do not implement until the exact predicate URI, signer workflow identity, trusted-builder isolation, independent storage provider, retention SLA, recovery operator, and privacy classification are separately approved. No claim is made that an existing attestation, manifest, independent store, or end-to-end recovery test currently exists.
- **TDD boundary:** no production behavior or test code changed in this documentation-only finding. The TDD skill applies to later implementation; no RED/GREEN cycle or test pass is claimed here.
